# Omatune v0.1 Implementation Phases

## Purpose

This document breaks the v0.1 milestone into reviewable implementation
phases.

The goal is to keep work ordered and small:

-   establish process and protocol boundaries early;
-   land deterministic note/math logic before live audio complexity;
-   validate output and input paths independently before full UI polish;
-   finish with failure handling and verification rather than treating
    them as cleanup.

## Phase 1: Foundation And Process Wiring

Goal:
Create the plugin/helper skeleton and prove that the UI can start one
persistent helper process and receive protocol output.

Main ownership:

-   QML plugin entry and tuner widget shell
-   helper executable bootstrap
-   process lifecycle wiring

Dependencies:

-   none

Work in this phase:

-   create the initial repository code layout;
-   choose and wire the Omarchy/Quickshell plugin entry points;
-   create the Rust helper executable;
-   make the helper emit `{"type":"ready"}` on successful startup;
-   ensure stdout is protocol-only and stderr is diagnostic-only;
-   ensure the UI does not poll by repeatedly spawning commands.

Done when:

-   activating the tuner starts one helper process;
-   the UI can observe helper readiness;
-   deactivating the tuner stops the helper cleanly;
-   the process boundary matches `docs/protocol.md`.

Verification:

-   `omarchy plugin validate /home/jklh/Projects/omatone`;
-   manual helper launch smoke test;
-   manual UI activation/deactivation test;
-   confirm stdout contains NDJSON protocol messages only.

## Phase 2: Note Model, Parsing, And Protocol Types

Goal:
Implement the deterministic core logic before live audio work.

Main ownership:

-   Rust note/frequency module
-   Rust protocol command/message types
-   unit tests for musical math and parsing

Dependencies:

-   Phase 1

Work in this phase:

-   implement note parsing and canonicalization;
-   implement note -> frequency conversion;
-   implement frequency -> nearest note conversion;
-   implement cents calculation;
-   define protocol command/message structs and parsing behavior;
-   reject malformed commands and invalid notes safely.

Done when:

-   standard reference values like A2, A3, A4, and A5 test correctly;
-   guitar shortcuts are derived through the general note model;
-   invalid note input cannot produce unsafe numeric output;
-   protocol parsing failures are recoverable.

Verification:

-   unit tests for note parsing;
-   unit tests for note/frequency conversion;
-   unit tests near semitone boundaries;
-   unit tests for cents calculation;
-   unit tests for protocol command parsing.

## Phase 3: Reference-Tone Output Path

Goal:
Deliver useful reference-tone playback independently of pitch detection.

Main ownership:

-   Rust oscillator and output stream
-   play/stop tone command handling
-   tone state protocol emission

Dependencies:

-   Phase 1
-   Phase 2

Work in this phase:

-   open audio output through the chosen Linux audio backend;
-   generate a sine-wave reference tone from note + A4 reference;
-   add a short amplitude ramp for start/stop or tone replacement;
-   implement `play_tone` and `stop_tone` handling;
-   emit `tone_started`, `tone_stopped`, and output-error states.

Done when:

-   arbitrary supported chromatic notes can be played;
-   changing notes replaces the active tone immediately;
-   output failures surface clearly without freezing the UI.

Verification:

-   unit or numerical tests for oscillator frequency;
-   helper CLI smoke tests for `play_tone`, `stop_tone`, and note
    replacement;
-   manual smoke test for start, stop, and note replacement;
-   manual error-path test if output device access can be denied safely.

## Phase 4: Microphone Capture And Pitch Detection

Goal:
Add live pitch detection while preserving the already working process and
tone output behavior.

Main ownership:

-   Rust input stream
-   pitch detector
-   no-signal and confidence behavior

Dependencies:

-   Phase 1
-   Phase 2
-   preferably Phase 3, so output and input behavior can be tested in the
    same helper process

Work in this phase:

-   open microphone input through the chosen backend;
-   feed analysis frames into a monophonic detector such as YIN or a
    comparable autocorrelation-based approach;
-   reject silence and obviously unusable frames;
-   calculate nearest note and cents from detected frequency;
-   emit `pitch` updates at a responsive cadence;
-   emit `no_signal` when pitch is not currently reliable.

Done when:

-   stable deterministic test signals are detected correctly;
-   no-signal behavior clears stale pitch state;
-   pitch updates feel continuous rather than bursty or laggy.

Verification:

-   tests against generated sine-wave signals;
-   tests across more than standard guitar range;
-   manual live-instrument smoke test;
-   measurement of approximate update cadence during steady input.

## Phase 5: QML UI Integration And Interaction

Goal:
Turn the working helper into a usable tuner experience in the Omarchy
bar.

Main ownership:

-   QML view state
-   protocol consumption
-   tone-selection interaction

Dependencies:

-   Phases 1 through 4

Work in this phase:

-   display detected note, frequency, and cents deviation;
-   render a responsive tuning indicator;
-   surface explicit no-signal and error states;
-   provide arbitrary chromatic reference-note selection;
-   provide the six standard guitar shortcuts;
-   allow restart or recovery after helper failure.

Done when:

-   a user can activate the tuner, play a note, and see continuous pitch
    feedback;
-   a user can start and stop reference tones from the UI;
-   UI behavior remains responsive when audio errors occur.

Verification:

-   manual end-to-end tuner test;
-   manual end-to-end reference-tone test;
-   manual restart/recovery test after forced helper exit or startup
    error.

## Phase 6: Hardening, Packaging, And Documentation Sync

Goal:
Finish v0.1 as a reliable small utility instead of stopping at the first
working demo.

Main ownership:

-   failure handling
-   installation/package layout
-   final documentation accuracy

Dependencies:

-   Phases 1 through 5

Work in this phase:

-   test repeated start/stop cycles;
-   test device unavailable and device disconnect paths where feasible;
-   confirm helper-exit behavior is surfaced cleanly in the UI;
-   make sure defaults and supported note behavior are documented;
-   update README and protocol/architecture docs to match shipped
    behavior.

Done when:

-   the main failure modes in `AGENTS.md` are handled without freezing the
    bar;
-   the shipped doc set matches the implemented behavior;
-   v0.1 success criteria from `README.md` are satisfied.

Verification:

-   end-to-end manual checklist covering activation, detection, tone
    playback, and restart;
-   full test suite for deterministic logic;
-   spot checks for helper stdout/stderr contract.

See `docs/v0.1-verification.md` for the current concrete checklist and
deterministic failure-simulation commands.

## Exit Criteria For v0.1

v0.1 is ready when all phases are complete and these user-visible
outcomes hold:

-   the tuner starts reliably from the Omarchy bar;
-   detected note, frequency, and cents update in real time;
-   silence and weak input do not leave stale pitch on screen;
-   arbitrary chromatic reference tones and guitar shortcuts work;
-   audio and helper failures are surfaced clearly and the tuner can be
    restarted.
