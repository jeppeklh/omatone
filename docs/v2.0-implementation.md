# Omatune v2.0 Implementation Phases

## Purpose

This document organizes the work from a stable `v1.0` tuner into a
deliberate `v2.0` release.

It does not replace `docs/roadmap.md`.

For the shipped `v1.5` UX baseline that precedes this work, see
`docs/v1.5-implementation.md` and `docs/v1.5-ux-review.md`.

-   roadmap items remain product directions;
-   phases here are implementation groupings;
-   `v2.0` should broaden Omatune's useful range without weakening the
    instant tuner workflow that justified `v1.0`;
-   the stable-width bar, concise hover summary, and `Tune` /
    `Reference` / `Metronome` / `Presets` / `Advanced` popup split from
    `v1.5` are the starting point, not open layout questions.

Post-`1.0` work is more speculative than the path to stability was. Add
only the features that improve real tuning or practice workflows while
keeping the helper, UI, and configuration contracts small enough to
document and verify clearly.

## Required Core Path

## Phase 1: Temperament Library, Target Model, And Preset-Pack Foundations

Goal:
Expand advanced tuning support into a shareable, validated model without
forking the chromatic engine into separate instrument-specific systems.

Roadmap coverage:

-   `Beyond 1.0` additional temperament libraries
-   `Beyond 1.0` more instrument/tuning preset packs
-   `Beyond 1.0` community-defined preset files

Main ownership:

-   `src/note.rs`
-   `src/config.rs`
-   preset and temperament schema docs
-   QML preset browser and import surface

Dependencies:

-   stable `v1.0`

Work in this phase:

-   promote the existing advanced tuning math into a documented
    temperament and note-target model that can scale beyond a few local
    offsets;
-   define a bounded preset-pack and temperament-pack schema that can be
    imported and exported without editing internal widget storage by
    hand;
-   keep detection targets, displayed note labels, and reference-tone
    generation on one Rust-owned source of truth;
-   allow additional built-in packs and locally shared packs without
    introducing a separate pitch engine per instrument family;
-   preserve `v1.0` defaults, validation rules, and additive migration
    behavior for existing users.

Done when:

-   shipped temperaments and preset packs cover meaningfully broader
    musical contexts without forking the pitch engine;
-   imported pack data is validated, normalized, and rejected clearly
    when unsupported;
-   users who never touch advanced tuning still get the same default
    `v1.0` workflow.

Verification:

-   temperament lookup and offset-math tests;
-   preset-pack parsing, normalization, and migration tests;
-   end-to-end checks that imported packs drive detection labels and
    reference tones consistently.

## Phase 2: Reference Audio Quality And Ear-Training Depth

Goal:
Make reference playback more musically useful for ear training and
ensemble contexts while staying immediate, bounded, and safe.

Roadmap coverage:

-   `Beyond 1.0` improved polyphonic reference sounds

Main ownership:

-   `src/reference_tone.rs`
-   `src/shared_audio.rs`
-   `src/audio_output.rs`
-   QML reference-scene controls

Dependencies:

-   Phase 1

Work in this phase:

-   improve interval and chord voicing, amplitude balancing, and ramp
    behavior so polyphonic references are clearer and less fatiguing;
-   keep waveform and voicing choices bounded rather than growing a
    general synth surface;
-   ensure all playback respects the active temperament and calibration
    model from Phase 1;
-   add only the smallest UI needed to choose richer reference scenes
    without crowding the default `Tune` destination;
-   protect latency, clipping safety, and tuner responsiveness as output
    scenes grow.

Done when:

-   polyphonic references are clearly more useful than the `v1.0`
    baseline, not just more configurable;
-   active tuning model and reference output always agree;
-   output changes remain immediate and artifact-free in normal use.

Verification:

-   numerical frequency and interval validation under multiple
    temperaments;
-   mixed-output bounds and clipping tests;
-   manual click, latency, and coexistence checks with live pitch
    detection.

## Phase 3: External Control And Omarchy Interoperability

Goal:
Let Omatune participate in larger practice workflows through small,
documented control surfaces instead of fragile UI coupling.

Roadmap coverage:

-   `Beyond 1.0` optional MIDI note input for selecting reference tones
-   `Beyond 1.0` integration points for other Omarchy musician plugins

Main ownership:

-   `src/protocol.rs`
-   `src/protocol_io.rs`
-   helper CLI and startup wiring
-   QML control-state integration
-   interoperability docs

Dependencies:

-   Phase 1
-   Phase 2 if external control can start richer reference scenes

Work in this phase:

-   define a minimal additive control surface for external note, preset,
    and transport actions;
-   add optional MIDI note input for selecting or retuning reference
    playback without forcing MIDI to exist on every system;
-   document how other local tools or plugins can trigger supported
    Omatune actions without scraping QML state;
-   keep failure handling explicit for unavailable MIDI devices,
    malformed external commands, and conflicting control sources;
-   avoid building a general automation, sequencing, or session-management
    layer.

Done when:

-   external triggers can select notes, presets, or small playback scenes
    through one stable contract;
-   unsupported environments fail clearly and leave the core tuner
    usable;
-   the default standalone workflow remains simple when no external
    integration is configured.

Verification:

-   protocol and command parsing tests for external-control additions;
-   deterministic mock MIDI tests;
-   manual interoperability checks with at least one other local
    workflow or script.

## Phase 4: Analysis Views And Power-User Feedback

Goal:
Expose deeper pitch information for advanced users without letting
diagnostic UI dominate the main tuner.

Roadmap coverage:

-   `Beyond 1.0` optional advanced pitch-analysis views

Main ownership:

-   `src/pitch_detection.rs`
-   `BarWidget.qml`
-   `Popup.qml`
-   visual and accessibility review docs

Dependencies:

-   Phase 1
-   Phase 2

Work in this phase:

-   define the smallest set of power-user views that materially help,
    such as short-term stability history, confidence detail, or compact
    note-trace views;
-   keep these views opt-in and visually secondary to the main tuner
    meter;
-   ensure displayed diagnostics reflect helper-owned state rather than
    QML-local guesses;
-   preserve accessibility, reduced-motion behavior, and compact layouts
    as new views are added;
-   reject analysis ideas that a dedicated spectrum or DAW-style tool
    would do better.

Done when:

-   advanced users can learn something actionable from the extra views;
-   the default `Tune` destination remains fast to parse for first-time
    tuning use;
-   analysis views do not create notable CPU or rendering regressions.

Verification:

-   manual default-path review with advanced views disabled;
-   performance spot checks with views enabled;
-   accessibility and reduced-motion checks;
-   regression tests for any newly exposed helper-side analysis
    calculations.

## Optional Pre-2.0 Expansion Path

These phases are candidates before `2.0`, not prerequisites. Include
them only if the required path remains small, documented, and low-risk.

Because post-`1.0` ecosystem work can sprawl quickly, ship optional
phases as narrow contracts and content packs rather than as open-ended
platforms.

## Phase 5: Community Content And Distribution

Goal:
Allow users to share useful tuning and temperament content without
turning Omatune into a hosted marketplace, sync service, or plugin
runtime.

Roadmap coverage:

-   `Beyond 1.0` community-defined preset files
-   `Beyond 1.0` more instrument/tuning preset packs
-   `Beyond 1.0` additional temperament libraries

Main ownership:

-   configuration and import/export surface
-   preset and temperament pack loader
-   documentation for the supported pack layout

Dependencies:

-   Phase 1

Work in this phase:

-   stabilize a documented pack format for community sharing;
-   ship a small curated set of additional packs as examples rather than
    as an unbounded catalog;
-   define compatibility and trust expectations for third-party packs;
-   keep discovery and installation deliberately simple and local;
-   avoid accounts, remote catalogs, or dynamic code loading.

Done when:

-   community packs can be shared and loaded predictably;
-   pack failures are bounded and diagnosable;
-   the local install path remains straightforward.

Verification:

-   fixture-based pack compatibility tests across versions;
-   malformed or unsupported pack rejection tests;
-   manual import, export, and install smoke tests.

## 2.0 Scope Gate

Before calling the project `2.0`, make one explicit scope decision:

-   the required phases must be complete;
-   optional phases should ship only as stable, bounded contracts;
-   every new control surface must remain documented and additive where
    possible;
-   no phase should weaken the instant tuner workflow or push Omatune
    toward DAW-style complexity.

## Exit Criteria For v2.0

`v2.0` is ready when these outcomes hold:

-   the `v1.0` tuner path remains accurate, responsive, and uncluttered;
-   advanced tuning content is broader, shareable, and validated;
-   richer reference audio remains musically useful, low-latency, and
    safe;
-   external control and interoperability behave predictably and fail
    clearly;
-   optional analysis views help power users without burdening first-time
    use;
-   configuration, content-pack, and control-surface docs are treated as
    stable contracts;
-   any optional ecosystem expansion included in `2.0` meets the same
    quality bar rather than arriving as a half-platform.
