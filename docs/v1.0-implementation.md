# Omatune v1.0 Implementation Phases

## Purpose

This document organizes the work from a complete `v0.1` tuner to a
stable `v1.0` release.

It does not replace `docs/roadmap.md`.

-   roadmap versions remain product milestones;
-   phases here are implementation groupings;
-   `v1.0` does not require every speculative expansion to ship before the
    tuner itself can be considered stable.

The stable chromatic tuner path is required. Metronome and other
musician-tool expansions remain conditional: include them before `1.0`
only if they meet the same quality and simplicity bar as the core tuner.

## Required Core Path

## Phase 1: Calibration, Persistence, And Preset Foundations

Goal:
Make the `v0.1` tuner configurable and repeatable without splitting the
single chromatic pitch model into instrument-specific engines.

Roadmap coverage:

-   `v0.2` adjustable reference A frequency
-   `v0.2` persisted reference-note and tuning choices
-   `v0.2` sharps/flats preference
-   `v0.2` built-in instrument/tuning presets
-   `v1.0` calibration support
-   `v1.0` flexible tuning presets
-   `v1.0` predictable configuration

Main ownership:

-   Rust note/tuning/config model
-   helper command/config surface
-   QML preset and preference controls
-   configuration schema and migration rules

Dependencies:

-   complete `v0.1`

Work in this phase:

-   expose the internal reference A parameter as a validated user-facing
    setting;
-   persist selected reference note, spelling preference, and last-used
    tuning state;
-   add built-in guitar, bass, ukulele, and useful violin-family presets
    as UI data over the general note model;
-   document the configuration schema and migration rules;
-   keep the protocol additive if helper settings need runtime updates.

Done when:

-   calibration changes affect both pitch interpretation and reference
    tones consistently;
-   last-used core settings survive restart cleanly;
-   preset selection does not fork or special-case the underlying pitch
    engine;
-   configuration defaults and migrations are documented.

Verification:

-   tests for calibrated note/frequency conversion;
-   config parsing and migration tests;
-   manual restart/persistence checks;
-   compatibility checks against `v0.1` defaults.

## Phase 2: Detection Quality, Stability, And Resource Efficiency

Goal:
Raise detection quality until the tuner feels trustworthy in ordinary
instrument-tuning conditions rather than only under clean synthetic
input.

Roadmap coverage:

-   `v0.3` noisy-room rejection
-   `v0.3` faster note lock
-   `v0.3` fewer octave errors
-   `v0.3` better low-frequency detection
-   `v0.3` confidence-aware stabilization
-   `v0.3` better silence handling
-   `v0.3` low CPU usage while active and near-zero overhead while
    inactive
-   `v1.0` accurate, responsive chromatic tuning
-   `v1.0` mature pitch detection
-   `v1.0` low resource usage

Main ownership:

-   `src/pitch_detection.rs`
-   `src/audio_input.rs`
-   regression corpus and detector tests
-   QML smoothing only where it does not change correctness

Dependencies:

-   Phase 1

Work in this phase:

-   improve rejection of noise, transients, and unstable frames;
-   reduce octave flips and slow relock behavior;
-   improve low-end performance for bass-range notes;
-   separate confidence, level, and displayed stability more clearly;
-   profile CPU and memory behavior for active and inactive states;
-   expand the regression suite from synthetic tones toward recorded and
    real-instrument validation.

Done when:

-   the tuner locks quickly enough to feel immediate;
-   octave errors are rare under normal monophonic use;
-   bass-range detection is usable beyond standard guitar;
-   idle overhead is negligible and active overhead is modest.

Verification:

-   expanded synthetic-tone and recorded-signal regression tests;
-   live validation on guitar plus at least one lower-pitched instrument;
-   spot CPU/memory profiling during active and inactive states;
-   latency/update-cadence measurements during steady input.

## Phase 3: Core UX, Accessibility, And Omarchy Polish

Goal:
Make the stable tuner exceptionally clear and native-feeling across real
Omarchy setups without turning the plugin into a large UI framework.

Roadmap coverage:

-   `v0.3` polished bar/popup behavior
-   `v0.3` keyboard-first operation
-   `v0.8` multiple compact meter presentations
-   `v0.8` display-density scaling
-   `v0.8` high-contrast feedback
-   `v0.8` reduced-motion behavior
-   `v0.8` non-color-only in-tune indication
-   `v0.8` compact and expanded popup layouts
-   `v0.8` native Omarchy theme integration
-   `v1.0` polished Omarchy integration
-   `v1.0` excellent standard-guitar workflow

Main ownership:

-   `BarWidget.qml`
-   `Popup.qml`
-   QML interaction model and keyboard flow
-   visual/accessibility review docs

Dependencies:

-   Phase 1
-   Phase 2

Work in this phase:

-   refine bar and popup layouts for horizontal and vertical bars;
-   add stronger keyboard navigation and activation paths;
-   make in-tune and error states readable without relying on color
    alone;
-   support reduced-motion and higher-contrast presentations where they
    materially improve clarity;
-   tighten the standard-guitar fast path so it is excellent with minimum
    clicks;
-   keep the default UI compact even if additional layouts are added.

Done when:

-   the tuner is comfortable to use from keyboard and mouse;
-   the standard-guitar workflow is fast and obvious;
-   the main states remain legible across different Omarchy themes and bar
    sizes;
-   additional presentation options do not fragment the UI model.

Verification:

-   manual UI checks across bar positions, densities, and theme
    combinations;
-   keyboard-only walkthroughs of the core tuner flow;
-   contrast and reduced-motion spot checks;
-   end-to-end validation of the guitar shortcut workflow.

## Phase 4: Hardening, Recovery, And Release Contract

Goal:
Turn the polished tuner into a release with a stable contract,
repeatable installation path, and well-tested recovery behavior.

Roadmap coverage:

-   `v0.9` long-running stability tests
-   `v0.9` device disconnect/reconnect tests
-   `v0.9` PipeWire restart recovery
-   `v0.9` helper crash recovery
-   `v0.9` protocol error and fuzz tests
-   `v0.9` configuration migration tests
-   `v0.9` installation and upgrade testing
-   `v0.9` stable CLI behavior
-   `v0.9` stable helper protocol
-   `v0.9` stable configuration schema
-   `v0.9` documentation audit
-   `v1.0` reliable PipeWire behavior
-   `v1.0` stable helper protocol
-   `v1.0` straightforward installation/updating
-   `v1.0` complete user and contributor documentation

Main ownership:

-   helper lifecycle and recovery behavior
-   packaged helper layout and launcher behavior
-   protocol/config stability guarantees
-   release and verification documentation

Dependencies:

-   Phase 1
-   Phase 2
-   Phase 3

Work in this phase:

-   expand failure simulation and long-running tests;
-   confirm restart behavior after helper crash, audio failure, and host
    restarts where feasible;
-   lock down the packaged helper and installation/update path;
-   finalize protocol and config compatibility rules;
-   audit documentation against the shipped behavior rather than design
    intent alone.

Done when:

-   the main runtime failures are recoverable or fail clearly without
    freezing the bar;
-   installation and update steps are straightforward and documented;
-   helper protocol, CLI behavior, and configuration semantics are stable
    enough to treat as a `1.0` contract;
-   docs, tests, and runtime behavior agree.

Verification:

-   long-running stability pass;
-   deterministic failure simulation and fuzz tests;
-   install/update/remove smoke tests;
-   final manual checklist derived from the shipped docs.

## Optional Pre-1.0 Expansion Path

These phases are candidates before `1.0`, not prerequisites. Include
them only if they do not destabilize the required core path.

Because each optional phase groups several roadmap ideas, implement them
in stable slices rather than as all-or-nothing umbrellas. If an early
slice ships cleanly, later slices can be deferred without treating the
earlier slice as incomplete.

## Phase 5: Ear-Tuning And Shared Output Expansion

Goal:
Broaden the reference-tone system from today's single sustained sine
note into a small set of genuinely useful ear-tuning tools without
turning the output path into a general-purpose mixer.

Roadmap coverage:

-   `v0.4` drone mode
-   `v0.4` continuous reference notes
-   `v0.4` reference intervals
-   `v0.4` simple reference chords
-   `v0.4` fast octave changes
-   `v0.4` keyboard note navigation

Main ownership:

-   `src/reference_tone.rs`
-   `src/audio_output.rs`
-   helper/UI playback protocol if additive commands are needed
-   QML reference-tone controls
-   shared output scheduling/mixing rules

Dependencies:

-   Phase 1
-   Phase 2

Recommended implementation slices:

-   `5A` single-note workflow polish
-   `5B` controlled interval and drone playback
-   `5C` simple chord presets only if `5B` stays clean

Work in this phase:

-   treat existing continuous single-note playback as the baseline, then
    clarify what additional `drone mode` behavior is actually required;
-   define and document the smallest helper/UI playback contract that
    can cover single-note playback plus any later interval or chord
    expansion;
-   keep `5A` focused on faster keyboard-driven pitch-class and octave
    navigation, immediate note replacement, and compact UI controls;
-   for `5B`, extend output from one tone to a bounded set of
    simultaneously generated notes rather than arbitrary user-programmed
    layers;
-   for `5C`, add only a small fixed set of musically common chord
    shapes over the same chromatic note model rather than inventing a
    separate chord engine;
-   keep clicks, latency, output-level safety, and tuner responsiveness
    under control as the output engine grows.

Done when:

-   the single-note path remains as immediate and reliable as before;
-   any added interval or chord mode is represented by one documented
    playback contract rather than special-case UI behavior;
-   richer reference tools feel immediate and musically useful;
-   output expansion does not break tuner responsiveness;
-   the UI stays compact and learnable.

Verification:

-   numerical validation of generated frequencies in every supported
    playback mode;
-   protocol and command parsing tests for any additive playback
    commands;
-   manual latency and click checks for note, octave, and playback-mode
    changes;
-   coexistence tests with live pitch detection active.

## Phase 6: Metronome And Audio Coordination

Goal:
Add a precise practice clock only if it can share the existing audio path
predictably with tuning and reference-tone features.

Roadmap coverage:

-   `v0.5` metronome scope

Main ownership:

-   shared audio scheduling/mixing
-   metronome timing and persistence model
-   QML metronome controls and beat indication

Dependencies:

-   Phase 5 is strongly preferred, especially if shared output behavior
    was already clarified in `5B`

Recommended implementation slices:

-   `6A` shared audio contract and scheduling rules
-   `6B` minimal metronome with credible timing
-   `6C` extended rhythm controls only if `6B` is stable

Work in this phase:

-   define one shared output policy before adding several metronome
    controls: how tuner capture, reference tones, and metronome audio
    coexist, mix, pause, or interrupt one another;
-   keep `6A` focused on ownership, scheduling, and documented runtime
    behavior rather than immediately broadening the UI;
-   make `6B` the first shippable slice: start/stop, BPM, a compact beat
    indication, and beat-one accent behavior with timing good enough for
    real practice;
-   add tap tempo, meter, subdivision, and extra shortcuts in `6C` only
    after the minimal timing path is stable;
-   persist metronome settings only if the config contract remains small
    and predictable;
-   avoid expanding toward sequencing, pattern editing, or drum-machine
    behavior.

Done when:

-   beat timing is reliable and immediate;
-   start/stop behavior remains immediate even while reference-tone or
    tuner activity is present;
-   metronome state is predictable alongside tuner and tone playback;
-   the feature still feels like a native bar utility rather than a
    separate application.

Verification:

-   timing-accuracy spot checks;
-   coexistence tests with reference tones and tuner capture;
-   restart/recovery checks while the metronome is active;
-   manual keyboard and start/stop workflow checks.

## Phase 7: Practice Workflow And Advanced Tuning Models

Goal:
Support more advanced users without complicating the default tuner path.

Roadmap coverage:

-   `v0.6` favorites, recents, and quick-switch workflow
-   `v0.6` import/export of human-readable configuration
-   `v0.7` advanced tuning and temperament work

Main ownership:

-   configuration and preset model
-   advanced note/temperament math
-   QML workflow shortcuts and advanced settings UI

Dependencies:

-   Phase 1
-   Phase 2 for any change that affects target-note math or detection
    range
-   optional dependence on Phase 5 and Phase 6 if favorites or presets
    span those features

Recommended implementation slices:

-   `7A` favorites, recents, and quick-switch workflow
-   `7B` human-readable import/export only after schema maturity
-   `7C` advanced tuning models only after ownership is clear

Work in this phase:

-   separate workflow shortcuts from tuning-model changes so simple
    favorites do not drag in advanced intonation complexity;
-   add favorites, recents, quick-switch behavior, or named presets only
    where they reduce real repeated friction;
-   add human-readable import/export only if the schema is already stable
    enough to treat the exported format as a supported contract;
-   add advanced tuning constructs such as temperaments, note offsets,
    capo awareness, transposition helpers, or detected-range changes
    only if Rust can own them as general note-target math rather than as
    UI-only exceptions;
-   keep the default workflow simple and uncluttered.

Done when:

-   repeated practice setup is materially faster where workflow features
    were added;
-   advanced users gain useful flexibility;
-   any advanced tuning model has one source of truth across detection,
    displayed targets, and reference-tone generation;
-   the default tuner remains easy for first-time use;
-   configuration growth stays understandable and documented.

Verification:

-   config migration and compatibility tests;
-   note/temperament/offset math tests;
-   end-to-end checks that detection, displayed targets, and generated
    reference frequencies agree under any advanced tuning mode;
-   manual default-path review to ensure advanced options do not dominate
    the UI.

## 1.0 Scope Gate

Before calling the project `1.0`, make one explicit scope decision:

-   required core phases must be complete;
-   optional phases should ship slice by slice rather than as partially
    implemented umbrella features;
-   optional phases ship only if they meet the same stability,
    documentation, and UX bar;
-   any optional slice that remains unstable or bloated should be
    deferred rather than weakening the tuner's `1.0` quality claim.

## Exit Criteria For v1.0

`v1.0` is ready when these outcomes hold:

-   chromatic tuning is accurate, responsive, and reliable;
-   the standard-guitar workflow is genuinely excellent;
-   calibration and flexible presets are supported without compromising
    the core note model;
-   reference tones are reliable and musically useful;
-   resource usage, recovery behavior, and installation flow are stable;
-   helper protocol, configuration, and contributor docs are treated as
    stable contracts;
-   optional expansions, if included, meet the same quality bar rather
    than arriving as unfinished extras.
