# Omatune v1.5 Implementation Plan

## Purpose

This document turns `docs/v1.5-ux-review.md` into an ordered
implementation plan for a focused `v1.5` cleanup release between stable
`v1.0` and broader `v2.0` feature work.

It does not replace `docs/roadmap.md` or `docs/v2.0-implementation.md`.

-   `v1.5` is a product-quality cleanup milestone, not a grab bag of UI
    experiments;
-   the goal is to remove current UI friction before expanding the
    product again;
-   unless a step explicitly says otherwise, helper protocol and audio
    behavior should remain unchanged.

## Scope

Ship these outcomes in `v1.5`:

-   stable bar footprint during note, tone, metronome, no-signal, and
    error transitions;
-   concise hover behavior;
-   substantially less always-visible meta text;
-   a calmer popup with task-based navigation instead of one long stacked
    flow;
-   standard-guitar actions kept prominent;
-   shorter, more scannable quick-switch labels.

Do not broaden scope in `v1.5` to add new audio features, new practice
tools, or new protocol surfaces unless a narrow implementation detail is
required by the UI cleanup.

## Confirmed Repository Facts

-   `BarWidget.qml` owns the bar label via `buttonText`, bar width via
    `implicitWidth: button.implicitWidth`, and hover text via
    `tooltipText`.
-   `Popup.qml` owns the entire popup layout inside one `Column {
    id: contentColumn }`.
-   The popup currently renders readout, status copy, keyboard legend,
    quick switches, quick notes, presets, reference controls, metronome,
    calibration, display controls, advanced tuning, and config transfer
    in one vertical flow.
-   Quick-switch labels are assembled in `BarWidget.qml`
    `quickSwitchButtonText()` from preset, reference scene,
    transposition, BPM, meter, and subdivision data.
-   The current `Expanded` or `Compact` mode is persisted through
    `popupLayoutMode` and shaped by `BarWidget.qml` plus `Popup.qml`.

## Selected Design

Use one stable-width bar presentation, one concise hover summary, and
one tabbed or segmented popup that defaults to a calm `Tune` view.

This is preferred over the smaller alternative of only deleting helper
text while keeping the current long scrolling layout and mutable bar
label. That smaller alternative would reduce copy, but it would still
leave the task-mixing problem, ambiguous bar states, and layout jank in
place.

Use these popup destinations:

-   `Tune`
-   `Reference`
-   `Metronome`
-   `Presets`
-   `Advanced`

## Phase 1: Stable Bar Surface

### Step 1. Stabilize the bar widget footprint

File path: `BarWidget.qml`

Exact symbols: root `implicitWidth`, `readonly property string buttonText`,
`WidgetButton { id: button }`

Current responsibility: derive the visible bar label directly from live
state and size the widget from that live text.

Required change: replace the current variable-width label model with a
bounded presentation model that keeps the widget width stable across
note detection, no-signal, tone playback, metronome playback, startup,
and error states. Prefer a fixed-width compact display model rather than
padding the current strings opportunistically.

Why this is the correct ownership location: `BarWidget.qml` already owns
the widget's visible label and width contract with Omarchy's bar.

What remains unchanged: the widget stays a single bar button, keeps the
same click actions, and still exposes active, dimmed, and urgent visual
states.

Dependencies: none.

Verification requirements: neighboring bar widgets no longer shift when
detected notes, cents, metronome BPM, or no-signal state change;
horizontal and vertical bar layouts remain stable.

### Step 2. Replace ambiguous bar-state language

File path: `BarWidget.qml`

Exact symbols: `readonly property string stateBadgeText`,
`readonly property string readoutTitleText`,
`readonly property string readoutFooterText`,
`readonly property string buttonText`

Current responsibility: map helper and playback state into user-visible
labels such as `SIG`, `M136`, note plus cents text, `ERR`, and `OFF`.

Required change: define a clearer compact state vocabulary for the bar
and readout. Remove `SIG` as the main no-signal label. If small icon
glyphs are used, use only glyphs already available in the current
Omarchy font path; otherwise use short fixed text labels that stay
clear.

Why this is the correct ownership location: the bar-visible state model
already originates from these computed properties.

What remains unchanged: helper state, tone state, and metronome state do
not move into QML-only shadow state.

Dependencies: Step 1.

Verification requirements: no-signal, tone-active, metronome-active,
starting, off, and error states are understandable without opening the
popup.

### Step 3. Reduce hover to a small summary

File path: `BarWidget.qml`

Exact symbols: `readonly property string tooltipText`

Current responsibility: render a large multi-line hover tooltip with
state, pitch, preset, A4, transposition, spelling, recovery, stderr,
keyboard shortcuts, and mouse controls.

Required change: replace the current tooltip dump with a short summary
that helps identify the current state without covering a large part of
the screen. Keep error-specific detail only when it materially helps
recovery. Remove the full shortcut legend from hover.

Why this is the correct ownership location: the hover content is defined
entirely in this property today.

What remains unchanged: hover may still expose a concise state summary,
and error states may still be more explicit than normal states.

Dependencies: Step 2.

Verification requirements: hover remains visually bounded; it no longer
reads like a second settings panel; error hover still helps identify the
failure class.

## Phase 2: Simpler Default Popup

### Step 4. Remove always-visible meta text from the default flow

File paths: `BarWidget.qml`, `Popup.qml`

Exact symbols: `readonly property string statusText`,
`readonly property string detailText`,
`readonly property string keyboardShortcutSummary`; in `Popup.qml`, the
`Text` nodes below `Rectangle { id: readoutCard }`, the quick-switch
description `Text`, the quick-note description `Text`, the metronome
hint `Text`, and the advanced explanatory `Text` blocks.

Current responsibility: keep large amounts of helper copy, status copy,
and shortcut guidance always visible in the main popup flow.

Required change: strip the default view down to essential state and
action cues. Move extended explanation, advanced guidance, and shortcut
reference behind later tabs or smaller secondary affordances instead of
keeping them permanently in the first view.

Why this is the correct ownership location: `BarWidget.qml` produces the
copy and `Popup.qml` decides where and when it is shown.

What remains unchanged: the implementation should keep keyboard support
and helpful runtime messaging; it should only change how much of that is
shown by default.

Dependencies: Phase 1 is preferred so the same simplified state model
drives both bar and popup copy.

Verification requirements: opening the popup no longer shows the full
shortcut legend or multiple paragraphs of gray helper text in the main
tuning path.

### Step 5. Rework the top header and readout into one calm tuning entry

File path: `Popup.qml`

Exact symbols: the first header `Column` inside `Column { id:
contentColumn }`, `Rectangle { id: readoutCard }`, `Column { id:
readoutColumn }`, `Button { id: powerButton }`

Current responsibility: render title, preset label, four top-row
buttons, readout card, then additional status and helper copy.

Required change: make the popup open into one clear tuning view built
around the readout card. Keep only the actions that belong in the first
screenful. Replace the current `Expanded` toggle with the new task
navigation from Phase 3. Move less-frequent actions such as restart to a
secondary location if they visually compete with core tuning use.

Why this is the correct ownership location: this block defines the first
impression and primary hierarchy of the popup.

What remains unchanged: the readout card remains the primary live tuning
surface; the popup stays anchored to the bar widget.

Dependencies: Step 4.

Verification requirements: the popup opens to a visually calm first
screen with clear hierarchy, minimal button noise, and no need to read
through helper paragraphs before tuning.

### Step 6. Keep standard guitar controls near the top of the default tab

File path: `Popup.qml`

Exact symbols: `Text { text: root.hostWidget ?
root.hostWidget.quickTuneHeadingText : "Quick tune" }`,
`Grid { id: quickNoteGrid }`, `Repeater { id: quickNoteRepeater }`

Current responsibility: show preset quick notes below quick-switch
history and several pieces of supporting copy.

Required change: keep the standard-guitar fast path prominently visible
in the default `Tune` destination. Do not require scrolling past
favorites, recents, or advanced controls to reach the six common guitar
notes.

Why this is the correct ownership location: this grid is the current
ownership point for the one-press preset note path.

What remains unchanged: existing `1` through `6` quick-note keyboard
actions and helper-side note playback logic stay intact.

Dependencies: Step 5.

Verification requirements: the standard `E A D G B E` quick notes are
visible immediately in the default guitar path and remain easy to use by
mouse and keyboard.

## Phase 3: Task-Based Popup Navigation

### Step 7. Add explicit popup navigation state

File path: `Popup.qml`

Exact symbols: `FocusScope { id: root }`, `PopupCard { id: popup }`,
`Column { id: contentColumn }`

Current responsibility: hold one popup tree with no explicit task-level
navigation state.

Required change: add one popup navigation state that selects the active
destination among `Tune`, `Reference`, `Metronome`, `Presets`, and
`Advanced`. Implement that selection as a compact tab row or segmented
control near the top of the popup.

Why this is the correct ownership location: the popup's information
architecture is owned entirely inside `Popup.qml`.

What remains unchanged: the popup remains a single anchored popup, not a
separate summoned panel or full application window.

Dependencies: Steps 4 through 6.

Verification requirements: the user can switch tasks without scrolling
through unrelated controls; `Tune` is the default destination on open.

### Step 8. Move existing controls into the new destinations

File path: `Popup.qml`

Exact symbols: `Column { id: quickSwitchColumn }`, `Grid { id:
quickNoteGrid }`, `Column { id: expandedContent }`, the `ButtonGroup`
for reference playback mode, `Grid { id: noteGrid }`, the note stepper
row, `Button { id: playToneButton }`, the metronome beat and BPM rows,
`Column { id: metronomeControlsColumn }`, `Column { id: controlsColumn
}`, `TextEdit { id: configTransferEditor }`

Current responsibility: render all workflows one after another in a
single scroll order.

Required change: rehome the existing controls into the new destinations.
Use this split:

-   `Tune`: readout card, minimal current-state text, quick guitar or
    preset-note actions;
-   `Reference`: playback mode, interval or chord shape, pitch-class
    grid, note stepping, octave changes, play or stop action;
-   `Metronome`: beat display, BPM controls, tap, meter, subdivision,
    start or stop action;
-   `Presets`: tuning presets, favorites, recents, and related quick
    switching;
-   `Advanced`: calibration, note spelling, transposition, config
    transfer, and any secondary recovery controls kept in the popup.

Why this is the correct ownership location: these components already own
the relevant controls; only their grouping and visibility need to be
restructured.

What remains unchanged: the same helper commands, persistence rules, and
underlying state model stay in place unless a later step explicitly
changes them.

Dependencies: Step 7.

Verification requirements: each destination feels focused on one job;
the user no longer needs to scroll through metronome, presets, and
configuration to perform a basic tuning action.

### Step 9. Update focus and shortcut behavior for the new layout

File path: `Popup.qml`

Exact symbols: `function focusInitialControl()`, the popup-scoped
`Shortcut` declarations, and the primary control ids such as
`powerButton`, `quickNoteRepeater`, `playToneButton`

Current responsibility: always focus the first quick note when possible
and keep popup shortcuts active while the popup is open.

Required change: make initial focus follow the selected destination and
keep the existing shortcut set working across the new layout. Add tab
selection shortcuts only if they are necessary after the reorganization;
do not grow a second shortcut legend just to compensate for clutter.

Why this is the correct ownership location: popup focus and keyboard
routing are already localized here.

What remains unchanged: keyboard support remains a first-class workflow,
and core domain shortcuts for notes, playback, and metronome stay
available.

Dependencies: Step 8.

Verification requirements: opening `Tune` focuses a useful tuning
control; switching destinations does not strand focus; existing note,
tone, and metronome shortcuts still work.

## Phase 4: Shorter Labels And Config Cleanup

### Step 10. Shorten favorites and recents labels

File path: `BarWidget.qml`

Exact symbols: `function quickSwitchButtonText(scene)`,
`function quickSwitchPresetSummary(scene)`,
`function quickSwitchSceneLabel(scene)`

Current responsibility: generate long quick-switch labels that combine
multiple fields into one button string.

Required change: replace the current verbose button text with a shorter,
scannable label strategy suited to compact popup buttons. Keep enough
information to distinguish scenes, but push lower-priority detail out of
the primary button text.

Why this is the correct ownership location: all quick-switch display
labels are already derived here before `Popup.qml` renders them.

What remains unchanged: quick-switch identity, deduplication,
fingerprinting, favorites, and recents behavior stay driven by the same
scene model.

Dependencies: Phase 3, because the new `Presets` destination will define
how much horizontal space these buttons actually need.

Verification requirements: favorites and recents are readable at a
glance and fit typical popup widths without dominating the screen.

### Step 11. Remove the old expanded or compact mode if tabs replace it

File paths: `BarWidget.qml`, `Popup.qml`, `docs/configuration.md`

Exact symbols: `readonly property bool popupExpanded`,
`function normalizePopupLayoutMode(value)`, the header button that
currently toggles `Compact` or `Expanded`, and the `popupLayoutMode`
field in `docs/configuration.md`

Current responsibility: preserve two popup layout modes across restarts
and show a top-row toggle between them.

Required change: if the new task-based popup makes the old compact or
expanded split redundant, remove the split instead of preserving it as a
second layout system. Update configuration docs and migration behavior so
older saved `popupLayoutMode` values are tolerated and ignored or
normalized cleanly.

Why this is the correct ownership location: the layout-mode state is
currently owned here and documented as persisted configuration.

What remains unchanged: high-contrast and reduced-motion accessibility
preferences should remain supported.

Dependencies: Phase 3.

Verification requirements: legacy settings containing `popupLayoutMode`
still load cleanly; the popup no longer shows an obsolete `Expanded`
button if the new navigation replaces that model.

### Step 12. Align the documentation with the shipped UX contract

File paths: `README.md`, `docs/v1.5-ux-review.md`,
`docs/v2.0-implementation.md`, and `docs/configuration.md` if Step 11
changes persisted state

Exact sections: documentation index in `README.md`, the purpose and
follow-up language in `docs/v1.5-ux-review.md`, and any configuration
sections describing popup layout behavior

Current responsibility: describe the current docs set and, in
configuration docs, the current persisted popup layout field.

Required change: update the docs to match the shipped `v1.5` UI model
instead of leaving the review and implementation docs disconnected from
the runtime behavior.

Why this is the correct ownership location: these files are the stable
human contract for the plugin's current UI behavior.

What remains unchanged: `docs/v2.0-implementation.md` continues to own
broader post-`1.0` feature expansion.

Dependencies: all earlier steps.

Verification requirements: a new contributor can read the docs and
understand the bar behavior, popup structure, and any config migration
without comparing against stale screenshots or old wording.

## Exit Criteria For v1.5

`v1.5` is ready when these outcomes hold:

-   the bar no longer changes width in ordinary tuning or metronome use;
-   hover is concise and non-disruptive;
-   the default popup view is calm and tune-first;
-   standard guitar remains a first-class fast path;
-   the popup is split into clear destinations instead of one long stack;
-   favorites and recents are scannable rather than verbose;
-   any configuration changes are documented and migrate cleanly.

## Verification Checklist

-   manual bar check while moving among no-signal, steady detected notes,
    reference-tone playback, metronome playback, startup, off, and error
    states;
-   hover sanity check on the bar widget in normal and error states;
-   popup first-open review with no scrolling required for the main
    guitar tuning path;
-   keyboard-only walkthrough across `Tune`, `Reference`, `Metronome`,
    `Presets`, and `Advanced`;
-   favorites and recents label review at typical popup widths;
-   persisted-settings migration check if `popupLayoutMode` is removed or
    normalized away.
