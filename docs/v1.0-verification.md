# Omatune v1.0 Verification

## Purpose

This document records the Phase 4 hardening checks for Omatune's stable
helper, launcher, recovery behavior, and install/update contract.

It complements `docs/v0.1-verification.md` rather than replacing it.

## Automated Checks

Run from the repository root:

```bash
cargo fmt --check
cargo test
omarchy plugin validate /home/jklh/Projects/omatone
bash scripts/build-helper-release.sh
bin/omatune-helper --version
```

The shared-audio foundation added for Phase 6A is covered by unit tests
inside `src/shared_audio.rs`. Those checks verify:

-   scheduled timed pulses wait until the requested frame offset;
-   stopping the reference-tone lane does not clear scheduled pulse work;
-   mixed output stays clamped to safe sample bounds.

The Phase 6C metronome timing model is covered by unit tests inside
`src/metronome.rs`. Those checks verify:

-   BPM validation;
-   supported meter and subdivision validation;
-   immediate downbeat start plus bar wraparound;
-   subdivision pulses land before the next primary beat;
-   stronger beat-one accent than later beats and stronger primary beats
    than subdivision clicks.

## Deterministic Helper Checks

For the protocol-sensitive cases below, prefer the integration tests in
`tests/helper_protocol.rs`. They keep stdin open until the expected
protocol observation arrives, which avoids flaky wall-clock sleeps.

### CLI Contract

```bash
cargo run --quiet --bin omatune-helper -- --help
cargo run --quiet --bin omatune-helper -- --version
bash scripts/run-helper.sh --version
```

Expected behavior:

-   `--help` prints the documented usage text and exits successfully;
-   `--version` prints `omatune-helper <version>` and exits
    successfully;
-   the launcher forwards CLI flags to the resolved helper;
-   an invalid `OMATUNE_HELPER_BIN` override fails clearly on stderr.

### Startup Input Failure

```bash
OMATUNE_TEST_INPUT_MODE=unavailable OMATUNE_TEST_OUTPUT_MODE=ok cargo run --quiet --bin omatune-helper
```

Expected stdout:

```json
{"type":"error","code":"audio_input_unavailable","message":"simulated microphone input unavailable"}
```

`ready` must not appear before that error.

### Repeated Startup Cycle

```bash
cargo test --test helper_protocol repeated_startup_cycles_keep_ready_before_no_signal -- --exact
```

Each run should emit:

```json
{"type":"ready"}
{"type":"no_signal"}
```

### Runtime Input Disconnect

```bash
cargo test --test helper_protocol runtime_input_disconnect_is_reported_after_ready -- --exact
```

Expected stdout:

```json
{"type":"ready"}
{"type":"error","code":"audio_input_disconnected","message":"simulated microphone input disconnected"}
```

### Unexpected Helper Exit

```bash
cargo test --test helper_protocol helper_can_exit_after_ready_for_recovery_testing -- --exact
```

Expected behavior:

-   stdout contains `{"type":"ready"}` before exit;
-   the process exits non-zero with code `91`.

This is the deterministic supervisor-side recovery case used by the
integration tests.

### Invalid Command Corpus

```bash
cargo test --test helper_protocol invalid_commands_do_not_crash_or_block_later_valid_commands -- --exact
```

Expected behavior:

-   each invalid command yields an `error` message;
-   the later valid `play_tone` and `stop_tone` commands still succeed;
-   the helper stays alive instead of crashing on malformed input.

### Metronome Command Surface

```bash
cargo test --test helper_protocol start_and_stop_metronome_work_without_real_audio_device_in_mock_mode -- --exact
cargo test --test helper_protocol restarting_metronome_with_a_new_bpm_restarts_on_the_downbeat -- --exact
cargo test --test helper_protocol metronome_start_can_echo_extended_meter_and_subdivision_state -- --exact
```

Expected behavior:

-   `start_metronome` emits `metronome_started` followed by an immediate
    downbeat `metronome_beat`;
-   additive `beat_unit`, `subdivision`, and `subdivision_step` fields
    echo the active rhythm state;
-   `stop_metronome` emits `metronome_stopped`;
-   repeating `start_metronome` with a new BPM restarts the bar on beat
    one.

## Install, Update, Remove Smoke Tests

1. Copy or sync the repository to
   `~/.config/omarchy/plugins/jeppeklh.omatune/`.
2. Run `bash scripts/build-helper-release.sh` in that plugin root.
3. Confirm `bin/omatune-helper` exists and is executable.
4. Run `omarchy plugin validate ~/.config/omarchy/plugins/jeppeklh.omatune`.
5. Load the widget, open the popup, and confirm helper startup reaches a
   `ready` or `no_signal` state.
6. Update the installed plugin contents, rerun
   `bash scripts/build-helper-release.sh`, and reopen the widget.
7. Confirm the updated helper still starts and reports the expected
   `--version` string.
8. Remove the plugin directory and remove the widget from the bar.

## Manual Recovery Checklist

1. Start the widget and confirm the popup leaves `OFF` cleanly.
2. Restart the helper from the popup and confirm the widget returns to a
   `ready` or `no_signal` state.
3. Trigger an input-side recovery path by disconnecting the input device
   or restarting PipeWire where feasible.
4. Confirm the widget enters a bounded recovering state instead of
   freezing and either returns to `ready`/`no_signal` or lands in a clear
   error state after retry exhaustion.
5. Trigger an output failure path and confirm the tone state clears
   without wedging the rest of the widget.
6. Start and stop the metronome, then change BPM, meter, and
   subdivision while it is active and confirm the beat indicator
   restarts on one.
7. Use tap tempo several times and confirm the BPM lands near the tapped
   pulse rate.
8. Confirm reference tone and metronome start/stop actions remain
   independent.
9. Leave the tuner running through repeated pitch, silence, tone-start,
   tone-stop, metronome-start, metronome-stop, and restart cycles.

## Long-Running Pass

Run one final manual stability pass before calling the release stable:

1. Leave the widget active for at least ten minutes.
2. Move between silence and steady notes repeatedly.
3. Start and stop multiple reference tones.
4. Start and stop the metronome and vary BPM, meter, subdivision, and
   tap tempo a few times.
5. Confirm the bar remains responsive, the helper does not flood stdout,
   and recovery controls still work.
