# Omatune v2.5 UI/UX Implementation Phases

## Purpose

This document turns post-`v2.0` hands-on UI and workflow feedback into a
focused `v2.5` implementation plan.

It does not replace `docs/roadmap.md`, `docs/v1.5-ux-review.md`, or
`docs/v2.0-implementation.md`.

-   `v2.5` is a coherence and usability release, not a feature grab bag;
-   the goal is to make the broader tuner, tone, and metronome surface
    feel deliberate and musician-readable;
-   audio and protocol changes are allowed only when they directly
    support a clearer workflow or a musically useful control that the
    current UI cannot express cleanly.

## Scope

Ship these outcomes in `v2.5`:

-   an icon-only bar widget with no changing note, `QUIET`, or other
    state text in the bar itself;
-   a popup whose tabs share a more consistent action layout and visual
    hierarchy;
-   a `Tune` path that always behaves as single-note tuning, regardless
    of what interval, chord, or voicing is selected elsewhere;
-   clearer naming for the tone tab, interval mode, and voicing choices;
-   a bounded but meaningfully broader interval, chord, and waveform
    surface;
-   documentation that stays in sync after meaningful UI/UX changes;
-   easy-to-find local development install, refresh, and removal
    commands.

Do not broaden scope in `v2.5` to add:

-   DAW-style analysis views or arrangement tools;
-   a general synth editor;
-   arbitrary user-authored chord builders or voicing editors;
-   more explanatory gray copy as a substitute for better layout,
    naming, or previews.

## Confirmed Repository Facts

-   `BarWidget.qml` still owns the visible bar surface through
    `readonly property string buttonText`, tooltip content through
    `readonly property string tooltipText`, and popup opening through the
    root `open()` and `toggle()` functions.
-   `Popup.qml` now has task destinations with a shared readout and a
    consistent header-plus-primary-action shell.
-   `Popup.qml` quick-tune buttons now call
    `root.hostWidget.playTuneNoteString(...)`, so `Tune` requests one-note
    playback without reusing the tone tab's playback shape.
-   `BarWidget.qml` currently names playback modes `single`, `drone`, and
    `chord`.
-   `BarWidget.qml` currently exposes voicing presets through
    `referenceScenePresets` with `blend` and `pedal` labels.
-   `BarWidget.qml` currently exposes only five interval presets
    (`3`, `4`, `5`, `7`, `12`) and four chord presets (`major`, `minor`,
    `sus2`, `sus4`).
-   `src/reference_tone.rs` already has two internal waveforms,
    `ReferenceToneWaveform::Sine` and `ReferenceToneWaveform::Warm`, but
    the UI does not currently let the user choose between them.
-   `src/reference_tone.rs` currently allows at most three positive
    intervals above the root (`MAX_REFERENCE_INTERVALS = 3`), which is
    already enough for the requested seventh-chord families.

## Selected Design

Use one icon-led bar button, one tabbed popup shell, and a strict
separation between tuning actions and tone-audition actions.

This is preferred over the smaller alternatives of only deleting more
copy or only adding more chord presets. Only deleting copy would leave
the current naming and action-placement confusion in place. Only adding
more intervals and chords would increase that confusion.

Use these popup destinations:

-   `Tune`
-   `Tone`
-   `Metronome`
-   `Presets`
-   `Advanced`

Within the tone destination, use these interaction terms:

-   `Single`
-   `Interval`
-   `Chord`

The current `blend` and `pedal` labels should be replaced by voicing
labels that say what the user will actually hear. A good target is a
pair such as `Close` and `Bass octave`, but the final wording should be
chosen only if it stays clear for both single-note and multi-note use.

## Phase 1: Icon-Only Bar And Consistent Popup Skeleton

Goal:
Replace the changing bar text with one fixed icon surface and make the
popup feel structurally consistent before broadening the tone library.

Main ownership:

-   `BarWidget.qml`
-   `Popup.qml`
-   `docs/v2.5-ui-ux-implementation.md`

Dependencies:

-   shipped `v2.0`

Work in this phase:

-   replace the current bar text states with a fixed icon or glyph model
    that does not show live notes, `QUIET`, `OFF`, or other changing text
    in the bar;
-   keep the bar footprint fixed across tuner, tone, and metronome
    states;
-   use color, activity dots, or similarly bounded indicators instead of
    changing text to show whether the helper, tone, or metronome is
    active;
-   reduce the tooltip to a tiny summary or remove it entirely if the bar
    icon and popup do enough work without it;
-   standardize the popup shell so the tab row, readout, and highest
    priority action for each tab live in a predictable place;
-   move `Restart` and other recovery actions out of the main tuning path
    when they visually compete with tuning.

Phase 1 implementation notes:

-   ship the bar as one fixed `♪` glyph plus three bounded activity
    markers ordered helper, tone, and metronome;
-   keep the hover summary to one compact line instead of the previous
    multi-line status dump;
-   give each popup destination a top header row with the destination
    title on the left and its primary action on the right;
-   keep audio recovery surfaced in `Advanced` instead of competing with
    the `Tune` path.

Done when:

-   the bar never shows live notes or `QUIET`-style state text;
-   neighboring widgets no longer react to Omatune text changes;
-   the popup tabs no longer feel like five unrelated micro-layouts.

Verification:

-   manual horizontal and vertical bar checks;
-   manual popup walkthrough across every destination;
-   default-path review with no large tooltip or status dump.

## Phase 2: Tune And Tone Separation

Goal:
Make `Tune` a strict single-note workflow and keep tone-audition state
from leaking back into quick tuning actions.

Main ownership:

-   `BarWidget.qml`
-   `Popup.qml`
-   helper command construction around `play_tone`

Dependencies:

-   Phase 1

Work in this phase:

-   rename the `Reference` destination to `Tone` at the UI layer;
-   give `Tune` its own one-press note action that always requests a
    single-note playback shape rather than reusing the active interval or
    chord selection from the tone tab;
-   ensure the `Tune` quick-note grid stays a pitch-target shortcut, not a
    mirror of the current tone-scene settings;
-   keep the tone destination responsible for interval, chord, voicing,
    and waveform state;
-   if any persisted UI label or documented user-facing naming changes,
    migrate additively and keep wire compatibility where practical.

Phase 2 implementation notes:

-   surface the second popup destination as `Tone` while keeping the
    internal destination id `reference` for compatibility;
-   route `Tune` quick-note buttons and the `1-8` keyboard shortcuts
    through note-only `play_tone` commands so they always audition one
    exact note;
-   leave the tone tab's saved playback mode, voicing scene, and shape
    state untouched when the user takes the `Tune` path;
-   no configuration migration is required for the tab rename because the
    stored ids and helper protocol stay unchanged.

Done when:

-   selecting `Chord` or `Interval` in the tone tab does not cause `Tune`
    quick notes to audition chords or intervals;
-   the tab naming better matches what the user is doing in each place;
-   `Tune` remains the fastest way to play one exact note and tune to it.

Verification:

-   manual checks that every quick-tune button always plays one note;
-   regression checks for selected tone playback outside `Tune`;
-   configuration migration checks if any persisted tab- or mode-facing
    naming changes are saved.

## Phase 3: Tone Vocabulary, Voicing Clarity, And Sound Character

Goal:
Make the tone tab readable without relying on gray explanatory text.

Main ownership:

-   `Popup.qml`
-   `BarWidget.qml`
-   `src/reference_tone.rs`
-   `docs/protocol.md`
-   `docs/configuration.md`
-   `docs/external-control.md`

Dependencies:

-   Phase 1
-   Phase 2

Work in this phase:

-   replace the UI label `drone` with `interval`;
-   replace `blend` and `pedal` with clearer musician-facing voicing
    labels;
-   explain voicing differences through compact direct previews such as
    voice chips or short voice summaries, not explanatory paragraphs;
-   surface a bounded waveform selector in the tone tab, starting from
    the already implemented internal `Sine` and `Warm` waveforms;
-   ensure waveform, voicing, and mode naming stay consistent between the
    popup, active readout, and any documented external control surface;
-   keep invalid or unsupported combinations explicit rather than hiding
    them behind ambiguous fallback behavior.

Done when:

-   users can tell what they will hear before pressing play;
-   the difference between the voicing options is clear without reading a
    gray paragraph;
-   `Interval` and `Chord` feel like musical terms rather than internal
    implementation vocabulary.

Verification:

-   manual label and layout review for all tone controls;
-   protocol and config doc audit for renamed user-facing concepts;
-   manual listening checks that waveform and voicing changes are obvious
    and immediate.

## Phase 4: Expanded Intervals, Chords, And Bounded Voicings

Goal:
Broaden the ear-training surface meaningfully without turning Omatune
into an open-ended harmony tool.

Main ownership:

-   `src/reference_tone.rs`
-   `BarWidget.qml`
-   `Popup.qml`
-   tone-related docs and protocol/config references

Dependencies:

-   Phase 2
-   Phase 3

Work in this phase:

-   expand the interval preset surface from the current small set to a
    broader but curated library of common intervals within the supported
    `1..=24` semitone engine range;
-   add seventh-chord families and related bounded chord presets,
    including at minimum dominant seventh, major seventh, minor seventh,
    minor-major seventh, half-diminished (`m7b5`), diminished, and
    diminished seventh, alongside the existing major, minor, sus2, and
    sus4 shapes;
-   allow compact musician-facing notation in labels such as `7`, `D7`,
    `Delta7`, `m7`, `mDelta7`, `m7b5`, `dim`, and `dim7`, while keeping
    any persisted or protocol ids stable and ASCII-safe;
-   review voice balancing and octave placement so the added presets are
    musically useful rather than merely more numerous;
-   keep the current three-extra-interval cap unless a specific later
    preset proves that a larger bounded voicing family is necessary.

Done when:

-   the tone tab covers clearly broader musical practice use than the
    current triad-only surface;
-   the added presets still feel curated and scannable;
-   seventh-chord families do not require a separate chord-engine model.

Verification:

-   numerical frequency and interval tests for the added presets;
-   clipping and balance checks for denser voicings;
-   manual review that the preset list remains scannable on the popup.

## Phase 5: Documentation Discipline And Local Development Hygiene

Goal:
Make meaningful UI/UX changes traceable and keep the temporary local
development install path easy to update or remove.

Main ownership:

-   `README.md`
-   `docs/v2.5-ui-ux-implementation.md`
-   `docs/omarchy-plugin-model.md`

Dependencies:

-   none

Work in this phase:

-   require every meaningful UI/UX change to update the relevant docs in
    the same change, not later;
-   keep a short changelog-style summary in user-facing communication
    after meaningful UI/UX work so the visible behavior change is called
    out explicitly;
-   document the current local rsync-based plugin install, refresh, and
    removal flow in a place that is easier to find than chat history;
-   document that the current Omarchy validator rejects a symlinked plugin
    root, so local development should use a copied plugin directory;
-   keep local development commands minimal and copy-pasteable.

Done when:

-   contributors do not have to re-derive the temporary local install or
    removal commands;
-   meaningful UX changes are reflected in docs immediately;
-   the development workflow itself no longer creates avoidable confusion.

Verification:

-   documentation review after each meaningful UI/UX change;
-   one manual local install, refresh, and remove smoke test;
-   confirmation that the documented commands match the validator's
    current behavior on this machine.

## Local Development Commands

Current local development install using a copied plugin directory:

```bash
bash /home/jklh/Projects/omatone/scripts/build-helper-release.sh
mkdir -p ~/.config/omarchy/plugins/jeppeklh.omatune
rsync -a --delete --exclude ".git/" --exclude "target/" /home/jklh/Projects/omatone/ ~/.config/omarchy/plugins/jeppeklh.omatune/
omarchy plugin validate ~/.config/omarchy/plugins/jeppeklh.omatune
omarchy shell shell rescanPlugins
omarchy plugin enable jeppeklh.omatune
omarchy restart shell
```

Refresh the copied plugin after local changes:

```bash
bash /home/jklh/Projects/omatone/scripts/build-helper-release.sh
rsync -a --delete --exclude ".git/" --exclude "target/" /home/jklh/Projects/omatone/ ~/.config/omarchy/plugins/jeppeklh.omatune/
omarchy restart shell
```

Remove the copied plugin again:

```bash
omarchy plugin disable jeppeklh.omatune
rm -rf ~/.config/omarchy/plugins/jeppeklh.omatune
omarchy shell shell rescanPlugins
omarchy restart shell
```

These commands remove only the copied plugin under
`~/.config/omarchy/plugins/jeppeklh.omatune/`. They do not delete the
repository at `/home/jklh/Projects/omatone`.

## Exit Criteria For v2.5

`v2.5` is ready when these outcomes hold:

-   the bar is icon-only and stable-width;
-   `Tune` no longer inherits interval or chord playback state from the
    tone tab;
-   the tone tab's naming is readable without gray explanatory prose;
-   primary actions feel consistently placed across tabs;
-   interval, chord, and waveform choices are broader but still curated;
-   local development install and removal commands remain easy to find and
    correct.
