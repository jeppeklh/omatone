# Omatune v1.5 UX Review

## Purpose

This document captures hands-on UX feedback from the current plugin build
for a focused `v1.5` UX cleanup milestone before broader `v2.0`
implementation work begins.

It complements `docs/v1.5-implementation.md`.

This is a product and interaction review, not a final implementation
plan.

The intent is to fix the current UI friction before expanding the
product further.

The `v1.5` cleanup has since shipped. Treat this document as the review
baseline and rationale behind the stable-width bar, concise hover
summary, and task-based popup destinations that now define the shipped
UI.

## Reviewed Pre-v1.5 Behavior

-   The bar widget width follows the live button label because
    `BarWidget.qml` binds `WidgetButton.text` to `buttonText` and sets
    `implicitWidth: button.implicitWidth`.
-   `buttonText` currently swaps among short state labels such as `OFF`,
    `SIG`, note plus cents text, reference-tone note labels, and
    `M<bpm>` metronome text.
-   `tooltipText` currently builds a large multi-line hover tooltip with
    state, pitch, preset, A4, transposition, spelling, recovery data,
    errors, the full keyboard shortcut legend, and click instructions.
-   The popup always shows secondary text below the main meter, including
    `statusText`, the full keyboard shortcut hint, and `detailText`.
-   The popup remains a single top-to-bottom control flow even in
    expanded mode.
-   Quick-switch buttons use long concatenated labels built from preset,
    reference scene, transposition, BPM, meter, and subdivision.

## User Feedback Summary

-   The core functionality is already there and worth preserving.
-   There is too much gray meta text and explanatory copy.
-   The bar label changes too often and causes visual jank.
-   `SIG` is not self-explanatory.
-   Seeing tuner or metronome activity in the bar is useful, but not when
    it keeps changing width and pushing nearby widgets around.
-   The popup feels crowded because too many different tasks live in one
    long vertical stack.
-   The hover tooltip is excessive and visually disruptive.

## Required UX Direction

### 1. Reduce Meta Text By Default

-   Remove or hide non-essential gray helper copy from the primary popup
    view.
-   Do not keep the full keyboard shortcut legend permanently visible in
    the main tuner flow.
-   Move extended explanations into optional help, advanced views, or a
    much shorter hover summary.

### 2. Stabilize The Bar Footprint

-   The bar widget should keep a predictable width across no-signal,
    detected-pitch, tone-active, and metronome-active states.
-   Real-time feedback in the bar is still valuable, but it should not
    reflow the bar on every note or state change.
-   Prefer fixed-width, icon-led, or otherwise bounded bar states over
    variable-length text as the primary design direction.

### 3. Replace Ambiguous State Labels

-   Do not use `SIG` as the main no-signal label.
-   Replace terse implementation-like abbreviations with clearer visual
    states.
-   Explore small tuning-fork, note, or metronome-style iconography where
    it improves recognition without adding clutter.

### 4. Tame Hover Behavior

-   Hover should be concise, narrow, and secondary.
-   Do not dump the full shortcut legend or configuration summary into a
    tooltip.
-   Hover should help identify the current state, not become a second
    control panel.

### 5. Rework Popup Information Architecture

-   Avoid one long stack where tuning, presets, favorites, reference
    tones, metronome, advanced tuning, and config transfer all compete
    equally for attention.
-   Split primary workflows into tabs, segmented navigation, or another
    comparably clear mode switch.
-   Keep the default path focused on immediate tuning use, not on showing
    every available feature at once.

### 6. Keep Standard Guitar First-Class

-   Common `E A D G B E` tuning actions should stay immediate and
    visually prominent.
-   The fast guitar path should not be buried below workflow history or
    advanced controls.

### 7. Shorten Workflow Labels

-   Quick-switch entries are currently too verbose and visually heavy.
-   Saved workflows should use short, scannable labels in the main UI.
-   Full scene detail should be secondary, not the primary button text.

## Shipped v1.5 UI Shape

This is the shipped structure that later work should treat as the UI
baseline unless a future phase intentionally changes it.

-   `Tune`: live pitch readout, cents meter, quick guitar notes, compact
    preset context
-   `Reference`: single, drone, and chord controls plus note selection
-   `Metronome`: BPM, tap, meter, subdivision, and running state
-   `Presets`: tuning presets, favorites, and recents
-   `Advanced`: calibration, note spelling, transposition, and config
    import/export

The current popup uses a compact top-row destination switch to keep the
default tuning path calm while leaving secondary workflows one click
away.

## Ownership Implications

-   `BarWidget.qml`: compact bar-state model, stable width behavior,
    concise hover behavior, and clearer iconography/state language
-   `Popup.qml`: reduced helper copy, clearer task grouping, shorter
    labels, and tabbed or segmented interaction flow
-   `src/config.rs` and `docs/configuration.md`: only if saved workflows
    gain short user-visible names or other persisted UI metadata
-   `docs/v2.0-implementation.md`: should treat this review as a completed
    precondition for broader `v2.0` UI work

## What Should Stay

-   The current tuner, reference-tone, preset, favorite, and metronome
    functionality
-   The ability to tell from the bar that something is active without
    opening the popup
-   Keyboard support, even if the full shortcut cheat sheet is no longer
    always visible

## Non-Goals

-   Do not turn the bar widget into a dense mini-dashboard.
-   Do not add more explanatory copy as a substitute for better layout.
-   Do not let optional power-user controls dominate the default tuner
    experience.

## Deferred Follow-Ups

These questions were intentionally left out of the shipped `v1.5`
contract and belong to later design work only if the runtime UX changes
again.

-   Should the bar default be fixed-width text, icon-only, or icon plus a
    very small badge?
-   Should favorites and recents support short user-defined names?
-   Should the metronome always keep its own destination, or ever merge
    back into another view?
-   Should hover show anything beyond a one-line state summary?
